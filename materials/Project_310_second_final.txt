ABSTRACT
Campus navigation remains a persistent challenge for new students, faculty, and visitors of Eastern International University (EIU), whose sprawling grounds contain multiple academic blocks, support facilities, parking areas, and pedestrian walkways that are insufficiently represented by commercial mapping platforms.
 This report documents the design, implementation of  a lightweight cross-platform mobile navigation application built with React Native and the Expo framework. The application renders a fully interactive Google Maps base layer augmented with custom spatial overlays derived from EIU's internal GIS data, originally encodefd as Shapefile layers and subsequently converted into the GeoJSON format. The routing core employs the A\* (A-star) pathfinding algorithm operating over a custom-built graph data structure whose nodes and edges are derived from the campus pedestrian road network. The Haversine formula is used as the heuristic for geographic distance estimation. 
The application provides point-to-point route planning between labelled landmarks, real-time GPS localisation via the device's native location services, and a polished bottom-sheet user interface.

CHAPTER 1. INTRODUCTION
1.1. Project Statement
Eastern International University occupies a large, multi-block campus in Binh Duong Province, Vietnam. The campus contains numerous academic buildings (Blocks B3, B8, B9, B10, B11), support facilities such as the Library, Canteen, and multiple Parking Zones, all connected by an internal network of pedestrian pathways and roads. New students, prospective applicants, visiting faculty, and delivery personnel frequently encounter difficulty locating specific facilities within this environment.
The problem is compounded by the fact that commercial mapping services such as Google Maps, Apple Maps, and HERE Maps do not capture the fine-grained internal road topology of private campuses. While these platforms accurately represent the surrounding urban street network, they do not possess data about the pedestrian walkways, named internal roads (e.g., "side-b10-gate4", "circle", "road-canteen"), or the precise spatial relationships between academic blocks within the EIU boundary. A user relying on Google Maps alone would receive no navigational guidance once they enter the campus gate.
This project addresses that gap by building a dedicated, lightweight mobile application â€” MyCampusApp â€” that provides indoor-grade navigation for the EIU campus using a custom GIS dataset. The application renders the campus map on top of a standard satellite/street base layer, overlays custom polygon and polyline layers derived from the university's own Shapefile data, and computes optimal walking routes between any two named landmarks using a graph-based pathfinding algorithm.
1.2. Background and Motivation
The proliferation of smartphones has made mobile mapping an essential daily tool for billions of users worldwide. Navigation applications have advanced from simple turn-by-turn street guidance to rich, context-aware platforms integrating indoor positioning, augmented reality, and real-time traffic data. Institutions such as universities, hospitals, airports, and shopping centres have increasingly recognised that commercial maps do not meet their internal wayfinding needs, motivating the development of purpose-built campus navigation solutions.
Several technical trends converge to make this project feasible without specialist hardware:
Cross-platform mobile development frameworks such as React Native allow a single TypeScript codebase to compile to both iOS and Android, significantly reducing engineering effort compared to native development in Swift/Objective-C and Kotlin/Java.
GIS-grade spatial data formats, particularly GeoJSON, provide a lightweight, human-readable encoding of geographic geometries (points, polylines, polygons) that can be bundled directly into a mobile application as a static asset â€” eliminating the need for a backend map tile server.
Graph-based pathfinding algorithms, specifically A\* (A-star), are well-established in computer science and offer optimal shortest-path solutions for the scale of a campus road network (typically fewer than 1,000 nodes), allowing computation to occur entirely on-device in under one millisecond.
The motivation for this specific project arose from the direct experience of students and visitors navigating the EIU campus. The campus's architecture â€” with parallel rows of similarly styled buildings â€” creates spatial disorientation, and the absence of visible directional signage compounds the problem. A digital navigation tool accessible on a personal smartphone represents the most scalable and low-maintenance solution.
1.3. Objectives and Scope
Objectives:
1. Develop a functional hybrid mobile application that renders the EIU campus boundary and internal road network as interactive map overlays.
2. Implement a graph-based routing engine (A\*) over the custom campus road dataset that computes optimal walking paths between any two named landmarks.
3. Provide real-time GPS localisation so that users can navigate from their current position.
4. Design and implement an intuitive, polished user interface featuring a full-screen map, custom building markers, and a draggable route-planning panel.
5. Bundle all spatial data as static application assets to eliminate any dependency on backend infrastructure.
Scope:
The application is geographically restricted to the EIU campus boundary polygon, defined by the coordinate extent approximately between latitudes 11.0498Â°N â€“ 11.0558Â°N and longitudes 106.6631Â°E â€“ 106.6690Â°E. The road network dataset covers all internal pedestrian walkways and vehicle roads within this boundary for which GIS data was available at the time of development. The twelve named landmarks included are: Block B3, Block B8, Block B9, Block B10, Block B11 (IT), the Library, the Canteen, the Recruitment Office, Parking Zones 1â€“4.
The scope explicitly excludes: outdoor navigation on public roads beyond the campus boundary, indoor floor-by-floor navigation within buildings, and real-time dynamic features such as event scheduling or crowd density mapping.
CHAPTER 2. RELATED WORKS
2.1. Campus Navigation Systems
Campus navigation systems have been an active area of research and commercial development for over a decade. Several approaches exist in the literature and in production:
Web-Based GIS Portals: Many universities publish static online maps built with ArcGIS Online, Google Maps Platform, or Leaflet.js. These portals present a browser-accessible map with clickable building markers but offer no turn-by-turn routing for pedestrians. Their primary limitation is the requirement for an internet browser and no mobile-native experience.
Dedicated Native Applications: Institutions such as MIT, Stanford, and the National University of Singapore have deployed iOS/Android applications that use the Google Maps SDK or Apple MapKit with custom overlays for internal navigation. These applications typically maintain a backend database of room-level points of interest and integrate with the institution's identity management system. Their limitation is the cost and complexity of maintaining two separate native codebases.
Hybrid Applications (React Native / Flutter): More recent campus navigation projects have adopted cross-platform frameworks. Hybrid Applications (React Native / Flutter): More recent campus navigation projects have adopted cross-platform frameworks. In these systems, bundling a pre-computed routing graph as a local JSON asset, rather than querying a remote routing server over the network, is a best practice that significantly reduces routing latency and enables offline navigation.
Indoor Navigation Research: For multi-storey buildings, GPS signals are unavailable, and researchers have explored Bluetooth Low Energy (BLE) beacon triangulation, Wi-Fi fingerprinting (Mirowski et al., 2013), and visual positioning systems (VPS) using computer vision. These approaches are beyond the scope of this project but represent important directions for future extension.
The approach taken by MyCampusApp most closely aligns with the static-asset hybrid model: all routing data is pre-processed and bundled with the application, ensuring that navigation functions correctly even without cellular network connectivity â€” a significant advantage in areas of poor coverage.
2.2. Cross-Platform Mobile Frameworks
The selection of a development framework is a foundational architectural decision that affects developer productivity, application performance, UI fidelity, and long-term maintainability. Three frameworks dominated consideration for this project:
Flutter (Dart, Google, 2018): Flutter compiles to native ARM code and uses its own rendering engine (Skia/Impeller) rather than platform-native UI widgets, producing highly consistent cross-platform appearance. Its map integration ecosystem (flutter_map, google_maps_flutter) is mature. However, Flutter's adoption of Dart â€” a language with limited prior exposure in academic curricula focused on JavaScript/TypeScript â€” was identified as a learning overhead risk for a time-constrained project.
React Native (JavaScript/TypeScript, Meta, 2015): React Native renders native platform UI components through a JavaScript bridge (or the newer JSI architecture), giving applications a genuinely native look and feel. Its ecosystem is extensive: the `react-native-maps` library provides a production-grade wrapper around both Google Maps SDK (Android) and Apple MapKit (iOS). Critically, the development team possessed prior experience in React, making the framework the most productive choice.
Ionic (Angular/React/Vue, HTML/CSS): Ionic wraps a web view inside a native shell, meaning the map rendering is performed by the browser engine rather than the native map SDK. This imposes significant performance penalties on map tile rendering and gesture handling, making it unsuitable for a map-centric application.
Decision: React Native with the Expo managed workflow was selected for the following reasons:
- TypeScript-first development with strong type safety for geographic coordinate types.
- `react-native-maps` provides direct access to Google Maps SDK with Polygon, Polyline, and Marker primitives needed for the spatial overlay system.
- Expo's managed workflow simplifies SDK integration (location, linear gradient, router) without requiring ejection to bare React Native.
- `expo-location` provides a unified, permission-managed GPS API across iOS and Android.

3.2. Spatial Data Architecture and Shapefile Processing
3.2.1. Input Data
The spatial dataset for EIU's campus was originally captured in the ESRI Shapefile format, an industry-standard binary vector format used by GIS software such as QGIS and ArcGIS. The dataset comprised two primary layers:
1. Polygon Layer (campus_buildings.json): Represents the closed boundary polygon of the campus perimeter and the footprints of individual buildings. Encoded as a GeoJSON `MultiPolygon` and `MultiLineString` FeatureCollection with WGS-84 coordinates.
2. Polyline Layer (streets.json): Represents the internal pedestrian and vehicle road network as a set of `MultiLineString` features. Each feature includes properties:
- `id` (integer): unique identifier
- `road` (string): Vietnamese road name/tag (e.g., "b8-b9", "gate-gate", "road-canteen")
- `length` (float): pre-computed segment length in metres

3.2.2. Data Conversion Pipeline
The Shapefile-to-application pipeline proceeded as follows:
1. QGIS Export: The original `.shp` Shapefile layers were opened in QGIS and exported to GeoJSON format using the "Save Features As" function with the WGS-84 (EPSG:4326) coordinate reference system.

3. Build-Time Bundle: At build time, the application bundler statically embeds both GeoJSON files directly into the application package. This means that all spatial data is available immediately upon launch without requiring any network connection or external server.

An important pre-processing decision was the introduction of a naming convention for road stubs that connect road segments to building interiors. Segments tagged with `road` values ending in `-in` (e.g., `"b8-in"`, `"b9-in"`, `"b10-in"`, `"lib-in"`) are excluded from the routing graph during construction. 3.3. Routing Algorithm and Data Flow
3.3.1. Graph Construction
The graph construction module reads the campus road dataset and builds an in-memory, bidirectional weighted graph using an adjacency list structure. This process occurs once at application startup and is shared across all subsequent route queries. The construction process is as follows:
1. Feature Iteration: Each GeoJSON Feature whose geometry type is `MultiLineString` is processed. Features with `road` ending in `-in` are skipped.
2. Coordinate Parsing: For each LineString within the MultiLineString, consecutive coordinate pairs are processed as directed edges. GeoJSON encodes coordinates as `[longitude, latitude]` (note: reversed from the conventional latitude-first order); this is corrected during parsing.
3. Node Key Generation: Each geographic coordinate is converted to a canonical string key by rounding to 5 decimal places (approximately 1-metre precision): `nodeKey(lat, lng) = "${lat.toFixed(5)},${lng.toFixed(5)}"`. This allows nearby-but-identical coordinates from different features to be correctly identified as the same graph node.
4. Edge Weight: The edge weight between two adjacent nodes is the Haversine great-circle distance in metres, computed by `haversine(lat1, lng1, lat2, lng2)`.
5. Bidirectional Edges: Both directions are added (fromâ†’to and toâ†’from), correctly modelling the pedestrian network as an undirected graph.

3.3.2. Snap-to-Graph
Because building entrance coordinates and GPS positions rarely fall exactly on a road network node, a nearest-neighbour search is performed before every route computation. This process scans all available nodes and identifies the one closest to the given coordinate using the Haversine formula. Given the relatively small size of the campus road network, this linear scan is fast enough to be performed in real time without any noticeable delay.
3.3.3. A\* Pathfinding
The routing engine implements the classic A* best-first search algorithm. Internally, the algorithm maintains three key data structures: a cost map that tracks the actual distance travelled from the start to each visited node (g-score), an estimated total cost map combining the actual distance with the heuristic distance to the goal (f-score), and a predecessor map used to reconstruct the final path once the destination is reached. A priority queue ordered by f-score ensures that the most promising node is always explored first.
Heuristic h(n): The Haversine distance from node n to the goal â€” an admissible heuristic since the straight-line distance never overestimates the true walking distance on a road network. This guarantees that A\* finds the globally optimal (shortest) path.
Algorithm Steps:
1. Initialise: push start node with f = h(start, goal); g(start) = 0.
2. Loop: pop the node with smallest fScore.
3. If current == goal: reconstruct path by following `cameFrom` pointers and return the ordered `LatLng[]` array.
4. For each neighbour: compute tentative g score. If better than previously recorded, update g/f scores, record predecessor, add to open set.
5. If open set empties without reaching goal: return `null` (no path exists).

3.3.4. End-to-End Data Flow
When a user initiates a route, the following sequence takes place:Â 1.Â Origin resolution:Â The starting point is determined either from the device's live GPS position or from a building the user has manually selected.Â 2.Â Snap to graph:Â Both the origin and destination coordinates are mapped to their nearest nodes on the campus road network, ensuring the route begins and ends on a valid road segment.Â 3.Â Route computation:Â The routing engine calculates the shortest path between the two snapped nodes and returns an ordered list of geographic waypoints.Â 4.Â Map rendering:Â The computed waypoints are drawn on the map as a visible route path.Â 5.Â Auto-zoom:Â The map camera automatically adjusts its zoom level and position to frame the entire route within the screen, accounting for the bottom control panel.
3.4. User Interface (UI) Design
3.4.1. Design Principles
The UI design of MyCampusApp follows a dark-mode navigation aesthetic, inspired by the UI patterns of Google Maps Night Mode, Apple Maps, and Waze. The design priorities were:
- Map visibility: The map must dominate the screen. Overlaid UI elements are minimal, semi-transparent where possible, and positioned at screen edges.
- Single-thumb reachability: The route planner controls are placed at the bottom of the screen, within comfortable reach of a user's thumb when holding a phone in one hand.
- Status clarity: The current route state (no route / route active) must be immediately legible at a glance.
3.4.2. Main Map Screen
The main screen is composed of the following layers:
- MapView (Full-screen): Google Maps with `mapType="standard"`, overlaid with:
- A semi-transparent blue-grey Polygon tracing the campus boundary.
- Custom Marker badges for each of the 12 landmarks (white pill with blue border; active destination highlighted in solid blue).
- The dual-layer route Polyline (white stroke, width 9, beneath the blue stroke, width 5) for a Google Maps navigation visual style.
- A "You are here" dot (pulsing blue circle) at the user's GPS position.
- Vignette gradients: Four `<LinearGradient>` overlays (top, bottom, left, right edges) provide a subtle darkening of the map perimeter, focusing the user's visual attention on the campus centre.
3.4.3. Route Panel (Bottom Sheet)
The route planner is implemented as a draggable bottom sheet panel that can be pulled up or pushed down by the user. It snaps smoothly between two fixed heights â€” an expanded state showing the full route controls, and a collapsed state showing only the panel title. The transition between states uses a spring animation, and the panel content fades in and out accordingly as the height changes.
3.4.4. Building Picker Modal
The building picker is presented as a full-screen modal that slides up from the bottom of the screen. It contains a real-time search bar that instantly filters the list of campus landmarks as the user types. A 'My Location' option is available at the top of the list when selecting the starting point, allowing users to navigate from their current GPS position. Each entry in the list displays the building's name and a short description, and tapping any item immediately sets it as the selected location and dismisses the modal.

The user expands the Route Planner panel by either tapping the handle pill or dragging upward. Within the modal, the user can type in the search bar to filter buildings by name (e.g., typing "b8" narrows the list to "Block 8").

4.2.3. Route Planning â€” Marker Tap Flow
As an alternative to the picker modal, the user can tap any building marker badge directly on the map. This sets the tapped building as the destination, uses the current GPS position (or previously selected origin) as the start, and computes the route immediately. The map then animates to the tapped building's location and displays the building's callout (name + description) after a short delay.
4.2.4. Route Display
Once calculated, the route is visually presented on the map as a clear blue path. To provide immediate context, the map automatically adjusts its zoom level and pans smoothly to frame the entire journey. The viewport is also padded to ensure that no part of the route is hidden behind the bottom control panel or screen edges.
4.2.5. Route Clearing
Whenever an active route is displayed on the map, a prominent 'Clear' button becomes available in the route planner panel. Tapping this button provides users with a quick and easy way to cancel their current navigation. It instantly removes the drawn path from the map and resets the selected locations, allowing the user to seamlessly start searching for a new destination.
4.2.6. Building Listing Panel
The application includes a scrollable directory panel listing all campus landmarks and their coordinates. This provides a convenient reference guide for users to quickly explore the university layout.
4.3. Demo Observations and Limitations.
4.3.1. Routing Correctness
During the demo, selected routes between campus landmarks were tested manually. The computed paths correctly followed the actual road network without cutting through buildings. Observations confirmed that the A* algorithm produced reasonable and visually accurate results for all tested cases.
4.3.2. Performance
Route computation was noticeably fast across all tested cases, with no visible delay from the user's perspective. Given the small scale of the campus road network, the algorithm performed adequately for the demo's purpose.
4.3.3. Limitation
One observed limitation during testing was occasional GPS inaccuracy near building facades, where signal interference may cause slight positional shifts. This is a known constraint of GNSS technology in dense environments and represents an area for improvement in future versions.
4.3.4. UI/UX Assessment
The overall interface was found to be straightforward during the demo phase. The draggable route panel and building search modal were easy to interact with. It was also noted that building markers can become visually crowded at lower zoom levels, which is a known limitation to be addressed in future iterations.

This project successfully demonstrated the core objectives through a functional prototype of a mobile campus navigation application for Eastern International University. The following outcomes were achieved during the demo phase:
Spatial Data Integration:Â EIU's GIS Shapefile data was successfully converted to GeoJSON format and embedded in the application as static assets, enabling fully offline routing without backend infrastructure.
Graph-Based Routing Engine:Â A custom A* pathfinding implementation over a campus road graph was able to produce reasonable walking routes between named landmarks with no noticeable delay during testing.
GPS Localisation:Â Real-time GPS tracking viaÂ expo-locationÂ was integrated to resolve the user's current position and enable "navigate from here" functionality.
User Interface:Â A dark-themed interface with a draggable bottom sheet, custom building badges, and route polylines was implemented, providing a clean and functional navigation experience for the demo.
Cross-Platform Deployment:Â The single TypeScript codebase targets both iOS and Android through the React Native/Expo managed workflow.

5.2. Future Works
Several directions for extending MyCampusApp are identified:
1. Zoom-Dependent Marker Clustering: At low zoom levels, overlapping building markers should be clustered into a single aggregate marker showing the count. At high zoom levels, individual markers should expand. Libraries such as `react-native-maps-super-cluster` support this pattern.
2. Indoor Floor-Level Navigation: The current system navigates between buildings but not within them. Extension to multi-storey indoor navigation could be achieved by integrating Wi-Fi fingerprinting positioning (using the device's Wi-Fi scan results against a pre-recorded fingerprint database) or BLE beacon triangulation, combined with floor-specific GeoJSON overlays for each building level.
3. Real-Time Campus Events Integration: A backend API could push location-tagged events (e.g., exam schedules, administrative notices) that appear as time-limited markers on the map.
4. Pedestrian Traffic Heatmaps: Anonymised, aggregated GPS telemetry from opted-in users could generate heatmaps indicating congestion on campus pathways at different times of day, enabling the routing engine to prefer less-congested routes.
5. Accessibility Routing: The road graph could be extended with attributes indicating accessibility features (ramp presence, step-free paths, covered walkways). Users requiring wheelchair-accessible routes or shelter from rain could request routing that prefers these edges.
6. Augmented Reality Wayfinding: Integration with the device camera via `expo-camera` and a compass sensor could provide an AR overlay showing directional arrows superimposed on the real-world view, similar to Google Maps Live View.
7. Automated Graph Maintenance: The current street graph is manually curated. A pipeline that automatically validates `streets.json` against the campus boundary polygon and detects disconnected components would improve maintainability as the campus develops.
